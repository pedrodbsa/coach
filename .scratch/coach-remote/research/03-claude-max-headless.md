# Can a headless Claude session on a remote server run on a Claude Max subscription?

**Research date:** 2026-07-22
**Question owner:** personal coaching system (Docker on remote Linux, webhook-triggered + daily cron)
**Status of this area:** volatile. Anthropic changed policy in Feb 2026, announced a further change for Jun 15 2026, then paused it on the day it was due. Re-verify before committing.

---

## Verdict

**Yes, with caveats — but only for one specific client, and the caveats are load-bearing.** Running the *official Claude Code CLI* headlessly (`claude -p`) on a remote Linux server, authenticated with a `CLAUDE_CODE_OAUTH_TOKEN` minted by `claude setup-token`, is explicitly documented and sanctioned by Anthropic for exactly this case: "CI pipelines, scripts, or other environments where interactive browser login isn't available." The token lasts one year, requires a Pro/Max/Team/Enterprise plan, and needs no API billing. That path is viable. Three things narrow it sharply. First, the *Claude Agent SDK* is a different answer: its own documentation says Anthropic "does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK," and directs you to API keys — while a separate Anthropic support article simultaneously states that Agent SDK and `claude -p` usage "still draw from your subscription's usage limits." Those two first-party statements are in genuine tension and I could not resolve it; do not build a system whose economics depend on the Agent SDK honouring a subscription. Second, token renewal is **not automatable** — `claude setup-token` opens a browser authorisation flow, so once a year a human must re-mint the token on a machine with a browser and update the server's env var. Third, an external orchestrator like n8n is the sharpest edge: n8n calling Anthropic directly with a subscription OAuth token is prohibited, while n8n *shell-executing the official `claude` binary* sits in a documented gap — Anthropic's login policy defines "third-party tools" broadly enough ("third-party software, tools, or services... including open-source projects") to arguably cover the orchestrator, but the actual API client remains Anthropic's own CLI. Not documented either way. **Finally, and this materially weakens the premise of the question: the API fallback for this workload costs roughly $45–80/month, which is at or below the price of the Max plans themselves.** The economics of the architecture do not collapse if the subscription route is rejected — they roughly break even.

## Findings

### 1. Auth mechanism — what is supported for a non-interactive session

Claude Code resolves credentials in a documented precedence order (first match wins):

| # | Credential | Header / mechanism | Notes |
|---|---|---|---|
| 1 | Cloud provider (`CLAUDE_CODE_USE_BEDROCK` / `_VERTEX` / `_FOUNDRY`) | provider-native | |
| 2 | `ANTHROPIC_AUTH_TOKEN` | `Authorization: Bearer` | for LLM gateways/proxies |
| 3 | `ANTHROPIC_API_KEY` | `X-Api-Key` | Console key, per-token billing. "In non-interactive mode (`-p`), the key is always used when present." |
| 4 | `apiKeyHelper` script output | returns a key | for rotating/vaulted credentials |
| 5 | **`CLAUDE_CODE_OAUTH_TOKEN`** | OAuth | **"A long-lived OAuth token generated by `claude setup-token`. Use this for CI pipelines and scripts where browser login isn't available."** |
| 6 | Subscription OAuth from `/login` | OAuth | default for Pro/Max/Team/Enterprise; interactive |

Source: [Authentication — Authentication precedence](https://code.claude.com/docs/en/authentication)

**The subscription-backed headless path is #5.** Verbatim from the same page, section *Generate a long-lived token*:

> For CI pipelines, scripts, or other environments where interactive browser login isn't available, generate a one-year OAuth token with `claude setup-token`:
> ```
> claude setup-token
> ```
> The command opens the same browser authorization flow as `/login`, and the token prints to the terminal after you approve access in the browser. It does not save the token anywhere; copy it and set it as the `CLAUDE_CODE_OAUTH_TOKEN` environment variable wherever you want to authenticate:
> ```
> export CLAUDE_CODE_OAUTH_TOKEN=your-token
> ```
> This token authenticates with your Claude subscription and requires a Pro, Max, Team, or Enterprise plan. It can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors. MCP servers you configure locally still work.

Two constraints attached to that token that matter for this build:

- **It cannot fetch claude.ai connectors** — locally configured MCP servers still work, which is what this system uses (Garmin MCP over stdio). Not a blocker.
- **`--bare` mode does not read it.** Verbatim: *"[Bare mode] does not read `CLAUDE_CODE_OAUTH_TOKEN`. If your script passes `--bare`, authenticate with `ANTHROPIC_API_KEY` or an `apiKeyHelper` instead."* Bare mode is otherwise the recommended mode for scripted/SDK calls and "will become the default for `-p` in a future release" ([Headless docs](https://code.claude.com/docs/en/headless)). **This is a forward-looking risk: the subscription token is incompatible with the mode Anthropic says is becoming the default for headless runs.**

Headless invocation itself is the `-p` / `--print` flag: `claude -p "prompt" --allowedTools "Read,Edit,Bash"`, with `--output-format json` giving a machine-readable result including `total_cost_usd` ([Headless docs](https://code.claude.com/docs/en/headless)).

**Agent SDK is a different answer.** The Agent SDK overview's *Set your API key* step carries this note verbatim:

> Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Please use the API key authentication methods described in this document instead.

Source: [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

The SDK docs list only `ANTHROPIC_API_KEY`, Bedrock, Claude Platform on AWS, Vertex, and Foundry as auth options. `CLAUDE_CODE_OAUTH_TOKEN` is not mentioned on that page.

**Contradicting first-party statement.** Anthropic's support article *Use the Claude Agent SDK with your Claude plan* currently opens with a pause notice:

> We're pausing the changes to Claude Agent SDK usage described below. For now, nothing has changed: Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription's usage limits.

Source: [Use the Claude Agent SDK with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)

The paused change (announced for 2026-06-15) would have moved Agent SDK, `claude -p`, GitHub Actions, and "third-party apps that authenticate with your Claude subscription through the Agent SDK" off subscription pools onto a monthly credit ($20 Pro / $100 Max 5x / $200 Max 20x), with overflow billed at API rates via usage credits.

**Assessment:** the support article's existence — and its enumeration of "third-party apps that authenticate with your Claude subscription through the Agent SDK" as a *covered category* — implies subscription auth for the Agent SDK is at least tolerated in practice, while the SDK's own docs say it is not allowed. This is unresolved. For a system whose viability depends on the answer, treat only the **Claude Code CLI + `CLAUDE_CODE_OAUTH_TOKEN`** path as documented-and-sanctioned.

### 2. Token lifetime and renewal

| Property | Value | Source |
|---|---|---|
| `claude setup-token` lifetime | **one year** | [Authentication](https://code.claude.com/docs/en/authentication) |
| Storage | not saved anywhere by the command; you copy it out of the terminal | same |
| Renewal | **re-run `claude setup-token`, which opens a browser authorization flow** | same |
| Plan requirement | Pro, Max, Team, or Enterprise | same |

**Renewal cannot be automated on a headless box.** The command "opens the same browser authorization flow as `/login`." There is no documented device-code, client-credentials, or refresh-token grant for minting a `setup-token`. The documented remedy for automation that cannot sign in interactively is precisely to generate the token elsewhere: the errors page lists, under *Login expired* → "For automation that can't sign in interactively," the instruction `claude setup-token`. So the operational shape is: mint on a laptop, transport the secret to the server, repeat annually.

**Expiry behaviour differs by credential.** From the [errors page](https://code.claude.com/docs/en/errors), the `Login expired` error — "Claude Code tried to renew your saved claude.ai or Claude Console login, and the OAuth service rejected the stored refresh token" — explicitly **does not** apply to `CLAUDE_CODE_OAUTH_TOKEN` sessions: *"Sessions authenticated with API key, `CLAUDE_CODE_OAUTH_TOKEN`, or third-party providers don't see this."* In non-interactive mode the message is `Failed to authenticate: OAuth session expired and could not be refreshed`.

Separately, an *interactive* `/login` credential (precedence #6, not what a server would use) now warns five days before expiry — `Your login expires in 3 days · run /login to renew` (Claude Code v2.1.203+) — and the docs note this matters specifically for unattended work: *"Renewing early matters most for sessions that run unattended."* Anthropic does not publish the `/login` credential's lifetime.

**Not documented:** what happens at the one-year boundary for a `setup-token` (hard stop vs. grace), whether any warning is emitted in `-p` mode, and whether the token can be revoked/rotated from a console UI.

### 3. Is headless/server use on a subscription sanctioned?

This splits three ways, and the distinctions are the whole answer.

**(a) Claude Code CLI, headless, on your own infrastructure — documented and sanctioned.**
`claude setup-token` exists for, and is described as being for, "CI pipelines, scripts, or other environments where interactive browser login isn't available." The [devcontainer docs](https://code.claude.com/docs/en/devcontainer) further document storing "a `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`" as a Codespaces secret to carry authentication into containers, and document `--dangerously-skip-permissions` for "unattended operation" inside a non-root container. Anthropic's login-policy article names Claude Code as a *native* application: subscription usage "is designed to support ordinary use of native Anthropic applications, including the Claude web, desktop, and mobile applications and Claude Code" ([Log in to your Claude account](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account)).

**(b) Third-party tools — subscription auth is disfavoured, and API keys are the stated preference.** Verbatim from the same login-policy article:

> Claude offers subscription plans (Free, Pro, Max, Team, Enterprise) that let subscribers authenticate using OAuth tokens or other methods. Subscription plans can only be used by subscribers, and the usage included in these plans is designed to support ordinary use of native Anthropic applications, including the Claude web, desktop, and mobile applications and Claude Code.

> The preferred way to access Anthropic services using third-party software, tools, or services ("third-party tools"), including open-source projects, is through API key authentication through Claude Console or a supported cloud provider. Anthropic may at its discretion allow paid subscribers who have enabled usage credits to use certain third-party tools to access Anthropic services included in paid subscription plans, but reserves the right to draw use of such third-party tools from usage credits rather than subscription limits.

> If you're building a product, application, or tool for others, use API key authentication through Claude Console or a supported cloud provider.

Note the last sentence's qualifier: *"for others."* A personal, single-user system is not obviously "for others." But the middle paragraph's definition of "third-party tools" has no such qualifier and explicitly sweeps in open-source projects.

**(c) The Feb 2026 hard line.** Widely reported (and consistent with the Agent SDK doc note above): on 2026-02-19 Anthropic updated documentation, and on 2026-02-20 its legal terms, to state that OAuth tokens from Claude Free/Pro/Max may not be used in any other product, tool, or service, including the Agent SDK. **I could not locate this sentence verbatim on a first-party page.** I checked [Consumer Terms](https://www.anthropic.com/legal/consumer-terms) (mentions no OAuth; does prohibit accessing the Services "through automated or non-human means, whether through a bot, script, or otherwise" *except* "when you are accessing our Services via an Anthropic API Key" or "where we otherwise explicitly permit it"), [Commercial Terms](https://www.anthropic.com/legal/commercial-terms) (silent; and states it does not govern consumer offerings), and the [Usage Policy](https://www.anthropic.com/legal/aup) (silent on this specifically). The quote circulates via secondary coverage — *[The Register, 2026-02-20](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/)* and others — **which I flag as unverified against a first-party page.** The first-party statement I *can* verify is the Agent SDK doc note in §1.

**Worth noting:** the Consumer Terms' automation clause is broad enough that a cron-driven script arguably needs the "where we otherwise explicitly permit it" carve-out — and `claude setup-token`'s documented purpose ("CI pipelines, scripts") reads as exactly such an explicit permission for the Claude Code CLI.

**Not documented anywhere I could find:** whether running the official CLI headlessly *for yourself* on a server you own is treated differently from running it on your laptop. Nothing states a device, location, or interactivity requirement. I make no claim about enforcement.

### 4. Limits that would bite

**Subscription limits (the relevant ones if you go the Max route):**

- Claude Code usage on Pro/Max is **shared with Claude chat**: *"usage limits are shared across Claude and Claude Code, meaning all activity in both tools counts against the same usage limits"* ([Use Claude Code with your Pro or Max plan](https://support.claude.com/en/articles/11145838-use-claude-code-with-your-pro-or-max-plan)). This is the biggest practical hazard: an unattended cron job can silently consume the same pool you use interactively.
- There are **three concurrent ceilings**, per the documented error strings ([errors](https://code.claude.com/docs/en/errors)):
  - `You've hit your session limit · resets 3:45pm` — a rolling window
  - `You've hit your weekly limit · resets Mon 12:00am`
  - `You've hit your Opus limit · resets 3:45pm` — model-specific
- Session and weekly limits are **shared across all models** — switching model does not restore access. The Opus limit is the exception: switching off Opus keeps you working.
- The rolling window is documented as **five hours** for Team/Enterprise seat allowances (*"a per-seat allowance that resets on a rolling five-hour window and a weekly window"* — [costs](https://code.claude.com/docs/en/costs)). The Pro/Max articles describe session + weekly windows without publishing the duration or any token figure.
- Max tiers: Max 5x is "5 times more usage per session than the Pro plan"; Max 20x is "20 times more" ([What is the Max plan?](https://support.claude.com/en/articles/11049741-what-is-the-max-plan)). Max plans have "two weekly usage limits: one that applies across all models and another for Sonnet models only." Anthropic reserves the right to apply "weekly and monthly caps or model and feature usage, at our discretion."
- **Anthropic publishes no numeric token/request limits for Pro or Max.** This is a real planning problem for an unattended system.
- Overflow requires **usage credits** to be enabled, which bill at standard API rates — i.e. the "no API billing" property is only preserved while you stay inside the opaque limits.

**No documented concurrency limit** for subscription Claude Code sessions. The only concurrency knob documented is client-side: `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` (default 5), recommended for high-volume runs.

**Relevant unattended-operation env vars** ([errors](https://code.claude.com/docs/en/errors)):
- `CLAUDE_CODE_RETRY_WATCHDOG=1` — "For CI/unattended sessions: retry capacity errors indefinitely"
- `CLAUDE_CODE_MAX_RETRIES` (default 10, max 15 without the watchdog)
- `API_TIMEOUT_MS` (default 600000)
- `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` — caps how long `-p` waits on background subagents (default 10 min)

**If you go the API-key route instead**, limits are the standard tier-based RPM/TPM ([rate limits](https://platform.claude.com/docs/en/api/rate-limits)), returning HTTP 429 with `retry-after`. For a single daily cron plus a handful of webhook calls, no tier limit is remotely close to binding.

### 5. Can an external orchestrator (n8n) drive it?

**Nothing in the auth model requires an interactive TTY.** `claude -p` reads stdin, writes stdout, and takes credentials from environment variables. The docs show it used in `package.json` scripts, piped from `git diff` and `cat`, and redirected to files. `CLAUDE_CODE_OAUTH_TOKEN` exists precisely so no browser/TTY is needed at run time. So the *mechanics* of an n8n Execute Command node shelling out to `claude -p` will work, and subscription auth survives, provided:

- you do **not** pass `--bare` (bare mode ignores `CLAUDE_CODE_OAUTH_TOKEN`);
- the env var is present in the child process n8n spawns;
- you handle the SIGTERM semantics — Claude Code aborts the turn, kills the Bash process tree, runs `SessionEnd` hooks, and exits **143** ([headless](https://code.claude.com/docs/en/headless));
- piped stdin stays under the **10 MB** cap (v2.1.128+).

**The policy question is the real one, and it is not answered by the docs.** Two readings:

- *Permissive:* the process that authenticates and calls Anthropic is the official `claude` binary — a "native Anthropic application" by the login-policy article's own naming. n8n is a process launcher, no different from `cron`, `make`, or a shell script. Anthropic itself documents `claude -p` being driven by npm scripts and CI runners.
- *Restrictive:* the login-policy article defines third-party tools as "third-party software, tools, or services... including open-source projects" used "to access Anthropic services." n8n is third-party open-source software being used to access Anthropic services. Under that reading the preferred path is an API key, and Anthropic "reserves the right to draw use of such third-party tools from usage credits rather than subscription limits."

I found **no first-party statement** distinguishing "third-party tool that calls the Anthropic API directly with your OAuth token" from "third-party tool that execs Anthropic's own CLI." That distinction is the crux and it is undocumented.

**What is unambiguous:** an n8n *Anthropic node* (or any HTTP node) sending a subscription OAuth token straight at `api.anthropic.com` is the exact pattern the Feb 2026 change targeted. Don't.

**Build-vs-buy read:** if the deciding factor is "can I safely build on subscription auth via n8n," the honest answer is *the documentation does not authorise it and does not forbid it*, and the cost delta that made the question urgent turns out to be small (§6). A design that keeps the orchestrator dumb — cron/webhook → shell → `claude -p` with an API key — removes the ambiguity entirely for roughly the price of the subscription you were trying to protect.

### 6. Fallback costing (API pricing)

**Current published pricing** ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing), per million tokens):

| Model | Input | 5m cache write | Cache read | Output |
|---|---|---|---|---|
| Claude Opus 4.8 | $5 | $6.25 | $0.50 | $25 |
| Claude Sonnet 5 (from 2026-09-01) | $3 | $3.75 | $0.30 | $15 |
| Claude Sonnet 5 (intro, to 2026-08-31) | $2 | $2.50 | $0.20 | $10 |
| Claude Haiku 4.5 | $1 | $1.25 | $0.10 | $5 |

Cache multipliers: 5-min write 1.25×, 1-hour write 2×, cache read 0.1× base input.
Note: Opus 4.7+ and Sonnet 5 use a newer tokenizer producing **~30% more tokens for the same text** — factored in below.

#### Assumptions (measured against this repo where possible)

Actual file sizes a `/plan` run pulls in (`wc -c`):

| File | Bytes |
|---|---|
| `protocols/current-status.md` | 69,533 |
| `protocols/skin-log.md` | 27,814 |
| `protocols/nutrition.md` | 25,604 |
| `protocols/strength-exercises.md` | 24,688 |
| `protocols/meal-rotation.md` | 22,042 |
| `protocols/running.md` | 18,912 |
| `protocols/training.md` | 17,550 |
| `.claude/commands/plan.md` | 9,755 |
| `AGENTS.md` | 5,936 |
| `protocols/daily-template.md` | 4,314 |
| prior day's logbook file | ~13,000–34,000 |

A run that reads the status file, the command, AGENTS.md, the template, 3–4 protocol files and yesterday's log lands around **180,000–220,000 characters ≈ 55,000–60,000 tokens** at ~3.5 chars/token (denser new tokenizer).

Full base-case model for one "plan the day" run:

| Component | Estimate |
|---|---|
| Claude Code system prompt + built-in tool defs | ~15,000 tok |
| File content read | ~57,000 tok |
| ~10 Garmin MCP round-trips (JSON results) | ~20,000 tok |
| MCP tool names (definitions deferred by default) | ~3,000 tok |
| **Final context size** | **~95,000 tok** |
| Assistant turns (tool round-trips + reasoning) | ~20 |
| Cumulative input across turns (context resent each turn, avg ~55k × 20) | ~1,100,000 tok |
| — of which cache **reads** (~90%) | ~1,000,000 tok |
| — cache **writes** (each new chunk written once ≈ final context) | ~95,000 tok |
| — fresh uncached input | ~20,000 tok |
| Output incl. thinking | ~15,000 tok |

#### Arithmetic — one plan run

**Claude Opus 4.8:**
```
cache reads   1,000,000 × $0.50 / 1M = $0.500
cache writes     95,000 × $6.25 / 1M = $0.594
fresh input      20,000 × $5.00 / 1M = $0.100
output           15,000 × $25.00 / 1M = $0.375
                                       -------
                                       $1.57 per run
```

**Claude Sonnet 5 (standard $3/$15):**
```
cache reads   1,000,000 × $0.30 / 1M = $0.300
cache writes     95,000 × $3.75 / 1M = $0.356
fresh input      20,000 × $3.00 / 1M = $0.060
output           15,000 × $15.00 / 1M = $0.225
                                       -------
                                       $0.94 per run
```

#### Small logging interactions

Each `/log` or `/skin` call cold-starts (prompt cache TTL is 5 minutes by default, so hours-apart calls get no cross-run cache benefit). Assume ~20k context, ~3 turns, ~50k cumulative cache reads, ~20k cache writes, ~5k fresh input, ~3k output:

- Opus 4.8: `(0.050×0.50) + (0.020×6.25) + (0.005×5) + (0.003×25)` = **$0.25/run**
- Sonnet 5: `(0.050×0.30) + (0.020×3.75) + (0.005×3) + (0.003×15)` = **$0.15/run**

#### Monthly total (30 plan runs + ~4 logging calls/day = 120)

| | Plan runs | Logging | **Total/month** |
|---|---|---|---|
| **Opus 4.8** | 30 × $1.57 = $47 | 120 × $0.25 = $30 | **~$77** |
| **Sonnet 5** | 30 × $0.94 = $28 | 120 × $0.15 = $18 | **~$46** |
| Mixed (Opus plan, Sonnet logging) | $47 | $18 | **~$65** |

**Sensitivity:** turn count and MCP payload size are the dominant uncertainties. A ±2× band gives roughly **$40–150/month on Opus**, **$25–90/month on Sonnet**. Levers that move it materially: run the plan on Sonnet 5 (−40%); use `--bare` to skip auto-discovery of hooks/skills/MCP/CLAUDE.md (cuts fixed context, and is *required* anyway if you use an API key); trim `current-status.md` (it alone is ~20k tokens, ~35% of the file-read budget, re-read on every turn); use `--max-turns` to bound runaway loops; cache the 1-hour TTL if plan and logging runs cluster.

#### The comparison that matters

Max 5x is **$100/month** ([claude.com/pricing](https://claude.com/pricing); corroborated by the paused credit tiers of $20 Pro / $100 Max 5x / $200 Max 20x in the [Agent SDK support article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)).

**Estimated API cost for this workload ($46–77/month) is below Max 5x.** So the framing "if the subscription route is not viable, the economics of the whole architecture change" does not hold on these numbers. Two caveats: (a) if the Max subscription is already being paid for *interactive* use, then subscription-backed automation is genuinely free-at-the-margin and API cost is purely additive; (b) API cost scales with usage while the subscription is flat — but the flat cap is opaque and shared with interactive use, so it is not obviously the safer choice for an unattended cron.

## Confidence and gaps

**High confidence (verified verbatim on first-party pages):**
- `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`, one-year lifetime, browser flow required to mint, Pro/Max/Team/Enterprise required, documented purpose is CI/scripts/no-browser environments.
- Full credential precedence order and header semantics.
- `--bare` does not read `CLAUDE_CODE_OAUTH_TOKEN`; bare mode is slated to become the `-p` default.
- Agent SDK docs direct you to API keys and state Anthropic does not allow third-party developers to offer claude.ai login/rate limits for their products including Agent SDK agents.
- The Agent SDK support article's pause notice (Agent SDK, `claude -p`, and third-party app usage currently still draw from subscription limits).
- Subscription usage is shared between Claude chat and Claude Code; session + weekly + Opus limit strings.
- All API pricing figures and cache multipliers.
- Login-policy wording on native applications and third-party tools.

**Medium confidence:**
- Cost model. Pricing inputs are exact; token-volume assumptions are estimates. File sizes are measured from this repo; turn count, MCP payload size, and cache-hit ratio are judged, not measured. Anthropic's own benchmark of "~$13 per developer per active day" for enterprise Claude Code makes a $1.57 heavy agent run plausible but does not confirm it.
- The five-hour rolling window applying to Pro/Max. Documented explicitly only for Team/Enterprise seat allowances; the Pro/Max articles describe session windows without stating the duration.

**Low confidence / could not establish:**
- **The exact Feb 2026 legal wording.** The much-quoted sentence ("The use of OAuth tokens obtained via Claude Free, Pro, or Max accounts in any other product, tool, or service is not permitted") does not appear on the Consumer Terms, Commercial Terms, or Usage Policy pages I fetched. It circulates only through secondary reporting. *Settled by:* finding the current first-party page that carries it, or asking Anthropic support directly.
- **Whether an external orchestrator exec'ing the official CLI counts as a "third-party tool."** Not addressed anywhere. This is the single most decision-relevant gap. *Settled by:* a written answer from Anthropic support/sales — not by testing, since a working request proves nothing about policy.
- **Numeric Pro/Max limits.** Anthropic publishes none. *Settled by:* empirically running the workload for a week and watching `/usage`, accepting that the numbers may change without notice.
- **Whether the Agent SDK will honour subscription auth going forward.** Anthropic said it is reworking the paused plan and will give advance notice. Genuinely unknowable today.
- **Behaviour at the one-year token boundary** in `-p` mode (hard failure vs. warning), and whether tokens can be revoked from a UI.
- **Concurrency limits** for subscription-backed sessions. No documented limit; only the client-side `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` knob.

**Only testable by trying it:** actual token consumption per plan run (instrument with `claude -p --output-format json | jq '.total_cost_usd'`, which reports per-model cost breakdown per invocation — this would replace the whole §6 estimate with measured data in one day of running).
